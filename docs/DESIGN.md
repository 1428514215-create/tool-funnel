# tool-funnel 设计说明

本文解释「为什么这样设计」，与 README 的「怎么用」互补。适合想改内核、或想判断
是否适配自己场景的读者。

## 1. 问题定位：不是「工具选择」，而是「候选集构造」

学术界谈 tool selection 常默认候选集已知且不大。真实业务 Agent 里，真正的痛点
是**候选集本身就是 1000 个**，而且：

- 无法为每个查询都跑一次模型来做预选（那等于把成本挪了个地方，还多了一次往返）；
- 业务域的边界是业务知识，不是模型能可靠推断的（「退款」到底算售后还是财务？）；
- 工具之间的关系（A 之后常跟 B）是**使用中涌现的**，没人能一开始写全。

因此本项目把任务重新定义为：**用极低的、与工具总量近似无关的确定性开销，把
1000 个候选可靠地压到个位数，同时保留一条永远走得通的退路。**

## 2. 为什么是「漏斗」而不是「分类器」

一个直觉做法是训练一个「查询 → 工具」的分类器。我们不这么做，因为：

- **训练数据饥渴**：上万工具、长尾分布，分类器在冷启动时表现糟糕，而冷启动恰
  恰是 Agent 上线第一天。
- **标签不稳定**：什么是「正确工具」本身就随业务演化，静态分类器会迅速过时。
- **不可解释**：夹在模型和真实工具之间，出错时无法回答「为什么没给我这个工具」。

漏斗用**分层收窄**替代一次性分类：每一层只做一个廉价、可解释、可独立替换的
决定；任何一层出错，后续层都有机会补救（词法层不认域、`expand()` 兜底）。

## 3. 四层的职责与取舍

### L1 业务域网关

- **输入**：查询文本。
- **输出**：`List[DomainScore]`，取 top-k（默认 2）。
- **手段**：策划触发词（最高权重）+ 学习先验 + 词法兜底。用词频-逆文档频率的
  思想，让稀有词比常见词更有区分度。
- **为什么不用模型**：域判定是**业务约定**，不是语义理解题。「退款」在你们的
  口径里归售后，模型不知道。把这层做成可编辑的配置 + 可学习，比让模型猜可靠。
- **永不返回空**：没有命中时回落到先验最高的域，保证漏斗总有起点。

### L2 阶段解析

- **动机**：一个域内部仍然太大（订单域 200 个工具）。但业务域天然有**阶段**
  （定位→查看→变更→核对），同一阶段的工具高度相关。
- **三条路，按性价比排序**：关键词命中 → 从「刚调用的工具」继承 → （可选）让
  模型在候选阶段里选一个。
- **`llm_pick` 是钩子而非依赖**：默认关闭；开启时也只让模型在**已命名的少数
  阶段**里选，不让它面对全量工具。

### L3 链路图 + 词法排序

- **链路**是「A 之后常跟 B」的加权有向图。三个性质很重要：
  - **时间衰减**：让图跟随最近行为，而不是被远古历史冻结。
  - **成功加权**：出错的调用降低贡献，图收敛到「真正跑通的链路」。
  - **跨域不封锁**：跨域边是一等公民（这正是「订单→物流」这类交接），只是轻微
    抑制，避免淹没域内链路。
- **冷启动**：`ToolSpec.next_hint` 提供静态先验，所以在没有任何真实流量时，漏斗
  的链路推荐就已经可用。真实观测（≥若干次）才会覆盖先验，且先验有下限保护，
  不会被一两次噪声抹掉。
- **词法排序**用 BM25 而非向量：无需外部服务、可复现、微秒级；语义召回作为
  **可选重排**（`semantic.py`）只作用于已经压小的候选短名单，成本上界可控。

### L4 参数预填

- **动机**：很多轮次成本不在「选错工具」，而在「参数不全 → 再问一轮」。
  `order.search` 已经产出 `order_id`，`order.get` 却还要模型再填一遍，纯属浪费。
- **优先级**：模型已给的 > 精确上下文键 > 声明的别名 > 字面默认 > 「谁产出了
  这个键」。绝不覆盖模型显式给的值。
- **`missing_required` 单独返回**：宿主可据此决定「还差关键参数，是问模型还是
  直接短路」，而不是把残缺调用丢给工具。

## 4. 学习闭环

三条学习路径，全部离线可跑（见 `learn.py`）：

| 路径 | 数据 | 效果 |
| --- | --- | --- |
| 链路重建 | 历史会话的调用序列 | 补齐配置里没写的 A→B |
| 触发词挖掘 | 历史查询 + 最终落到的域 | L1 越来越准 |
| 参数流 | A 的产出 ∩ B 的入参 | 预填从「猜名」变「按数据流」 |

**一个容易踩的坑**：把「会话经过的所有域」都算作查询的证据。这会教出
「订单 = 物流」这种错误关联。正确做法是**只取会话的入口域**——这也是
`Learner._mine_triggers` 的实现约束。

## 5. 正确性护栏

- **绝不硬隔离**：桥接工具 + `expand()`；猜错代价 = 一次廉价补充调用。
- **`expand()` 的副作用就是学习**：纠正被记为一条强边，同类错误不会重犯。
- **可解释**：`RouteResult.explanation` 逐层留痕；`ToolMatch.reason` 说明每个
  工具为什么被选中（lexical / chain / domain / stage / bridge / stage-default）。
- **可序列化**：目录与学习状态都是纯 JSON，便于版本管理、灰度、A/B。

## 6. 复杂度

设工具总数 N、查询词数 T、倒排 posting 长度 P：

- 建索引：O(N · 平均词数)，一次性。
- 单次路由：O(T · P) 检索 + O(候选数 log 候选数) 排序 + O(N) token 统计
  （已缓存为 O(1)）。**与 N 近似解耦**——这正是「工具越多越划算」的来源。
- 实测 1000 工具下单次路由毫秒级（纯 CPU，本机 p50 约 1–3 ms）。

## 7. v0.2：规模化运维（含 MCP）

v0.1 证明了四层漏斗在静态目录上有效。v0.2 解决的是「规模与时间」：目录会变、
流量会积累、工具生态在往 MCP 收敛。每个新机制都遵循同一条原则——**默认路径不
变，能力是加出来的**。

### 7.1 MCP 适配：为什么难，怎么解

MCP 是「一个 server 发布几十上百个工具」，正是漏斗的靶心。但接它有三处非平凡：

- **不能引入依赖。** 用鸭子类型（只要 session 有 `list_tools` / `call_tool`），
  官方异步客户端、嵌入式同步实现、测试假 session 都能用。核心保持零依赖。
- **不能丢信息。** MCP 的 `inputSchema` 可以有 `oneOf`、嵌套对象，漏斗的简化
  参数模型表达不了。所以**保留原始 schema**，交给模型的就是 server 原样发布的
  那份，漏斗只负责「少给几个」。
- **预填要真的能用。** 关键在 `structuredContent`：server 返回
  `{"orderId": "12345"}` 时，把这个标量**提到顶层**写进会话黑板，下一次
  `order.get` 才能被预填。这一步不做，适配器就只是「少传几个 schema」，
  做完了才是完整的省往返闭环。

MCP 不知道你的业务词汇（「订单」），所以业务域触发词仍需你补——这是有意的，
漏斗把「业务含义」和「工具发现」分开，前者是人的领域知识，后者才该自动化。

### 7.2 自适应预算：天花板不是目标

v0.1 的 `max_tools=6` 有个隐性浪费：某阶段只有 3 个工具时也会凑到 6，多出的
schema 纯粹是成本与注意力干扰。v0.2 把它变成**上限**：实际预算是「该域该阶段
真实存在的工具数」与上限的较小值，再加一道「弱于最优 15% 就砍」的尾部截断，
以及可选的整体 token 预算。原则是：**预算该表达成「最多花多少 token」，而不是
「最多给几个」**——后者会让一个描述很长的重工具挤掉两个轻工具。

### 7.3 链路的探索与蒸馏：一个只增不减的图会坏掉

链路图有两个对称的长期问题：

- **只跟涨会锁死。** 纯利用（永远跟最重的边）会让「早期偶然学到」的链路固化，
  更短更好的链路因为很少被试到而永远涨不起来。`explore` 用 UCB1 给稀有边一个
  探索加分，并在 `epsilon` 概率下把它换进可见集合——**换进可见集合**是关键，
  只重排而不浮现，那条边还是没有机会被调用、被观察。
- **只增会退化。** 每条观测到的转移都留一条边，长期运行后 `successors()`（要
  扫全图）从优化变成负担。`distill` 剪掉「权重和出现次数**都**低」的边——要求
  两者都低，才不会误杀一次刚学到、可能很有价值的新观测。

两者都遵循同一护栏：**先验（`next_hint`）永不被单次噪声抹掉**。

### 7.4 冷启动缓存：缓存是优化，不是正确性依赖

5000 工具建索引约 300ms，一次性，但短进程每次都付。`cache.py` 把索引与学习状态
落盘，用**内容签名**校验：目录变了，签名不匹配，缓存被忽略并正常重建——而不是
被信任。每条失败路径都降级为「重建」，绝不降级为「错误路由」。

### 7.5 阶段自动发现：从「人配」到「自长」

L2 的阶段以前要手写，这是通往「零配置」的最大障碍。`discovery.py` 从历史会话
学：工具在会话里的**归一化位置**（0=首个，1=末个）天然就是「阶段」这一维，用
确定性的一维 k-means（分位数播种，保证可复现）聚类即可。产物是普通的
`StageSpec` 列表，可 review、可手改。声明式配置永远优先于自动发现——**自动发现
是助手，不推翻人的显式意图**。

### 7.6 语义兜底与预填学习：只补短板，不抢主路

- **语义域兜底**只在一个触发词都没命中时才跑（`needs_semantics`），且只对
  **业务域**（寥寥几个）做 embedding，成本与工具总数无关。合并时是**加法**，
  所以强关键词命中永远不会被「看起来像」的 embedding 挤掉。
- **预填接受率**记录 suggested 值是否被模型采纳；其偏置被限幅在 ±0.25，只够
  在同等特异度的候选间换位，**绝不让学习出来的默认值压过显式上下文值**。

一句话总结 v0.2 的设计取向：**让漏斗在目录增长、流量积累、生态迁移（MCP）时
依然成立，且每一处自动化都保留一条「人可以覆盖」的退路。**

## 8. v0.3：自动索引 —— 从「人配」到「扔进去就能用」

v0.1/v0.2 都默认了一件事：**有人已经划分好了工具目录**。但现实里你往往只有一堆
工具。`toolfunnel/index.py` 就是把「代码库 → 索引」搬到「工具集 → 路由配置」上，
目标是一句话：**给一堆原始工具，交回一个已经能路由的漏斗**。

### 8.1 为什么不直接让模型分域

让模型把 1000 个工具分到若干域里，一次调用既慢又贵，还会漂移（同一批工具两次
分出来的域不一样），且不可复现。索引器选择**确定性算法 + 可解释输出**：用词频
相似度聚类、按动词定阶段、按对象连链路。产物是一份**普通 compose 文档**，人和
模型都能再改——推断是起点，不是终点。

### 8.2 三条推断，各自的依据

- **业务域**：TF-IDF 余弦 + 并查集单链聚类。关键取舍是**名字前缀当作强信号**：
  `order.search` 和 `order.get` 描述可能一字不重，但前缀相同几乎必然同域。只用
  词法会把它们拆开。
- **阶段**：看名字里的**动词**。这是唯一一处「先验定义」（`VERB_GROUPS`），因为它
  反映的是「读在前、写在后」这一普遍工作流，而非某个业务的私事。中英文动词都收。
- **链路**：同域内「读」类工具 → 共享同一对象的「写/核对」类工具。这是冷启动的
  种子，真实流量会覆盖它。

### 8.3 触发词挖掘里最容易踩的坑

第一版按「域内覆盖率」挖触发词，结果套话（"支持精确匹配"，出现在每个工具里）
覆盖率 100%，把真正的对象词（"订单"）挤掉了。修正的关键是**只看域外常见度**：
一个词在**本域**几乎人人有、在**域外**几乎没有，就是这个域的招牌词；只有当它
在域外也遍地都是，才判为套话。用域外 IDF 而非全局 IDF，还顺带修好了**单域目录**
（只有一个域时域外为空，什么都不该被抑制）。

### 8.4 性能：O(n³) → 稀疏并查集

第一版是 O(n³) 的平均连接凝聚聚类，200 个工具要 20 秒。改成两步：**只在共享词
汇（或共享前缀）的工具对之间算相似度**（倒排表给候选），再**并查集单链合并**。
1000 个工具 0.7 秒，2000 个 1.4 秒。

### 8.5 自由任务 / 无边界任务

漏斗从 v0.1 起就没假设「任务只属于一个域」。索引器把这条承诺再往前推一步：
**没能清晰归类的工具统一进 `general` 域**。于是「随便看看」这类没有明确触发词的
开放式查询，落点是「全部兜底工具 + 桥接」，而不是空集。这正是「无边界任务也能
快速用起来」的实现方式。

## 9. 已知边界与后续方向

- 工具数 < ~20 时收益有限，直接全量更省事。
- 域/阶段无法命名的高度流动场景，应先把 L1 退化为纯词法层。
- 自动索引的域划分对**命名规范的工具集**（`order.x`）远比对随意命名的好；名字毫无
  规律的目录，聚类只能靠描述文本，效果会打折——这时的正确做法是让它先跑一版，
  再人工微调输出文档。
- 可探索：真实 MCP server 的实测报告、多租户共享一份学习状态、把 UCB 换成
  Thompson 采样、在真实业务目录上发布评测基线。
